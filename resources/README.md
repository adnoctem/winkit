# Group Policy Management — LGPO Integration

Implementation specification for adding policy-as-code management to winkit via Microsoft's LGPO utility. Companion to the repository-wide
architecture document.

## Why LGPO and not direct registry writes

winkit already writes registry values directly via `Set-RegistryValue`. That works correctly for all policy paths (`Software\Policies\...`)
at the _application_ level — Chrome, Firefox, Office, Windows, etc. all read the same registry locations regardless of who wrote them.

The reason to layer LGPO on top is **auditability**, specifically for the path toward ISO 27001 certification. Settings written by LGPO
appear in:

- `gpresult /h <file.html>` — the supported Windows-native report
- `rsop.msc` — the supported Windows-native GUI
- `Get-GPOReport` (when running against a backup)

Settings written by direct `Set-ItemProperty` do **not** appear in any of these. They take effect identically, but to an auditor "I wrote it
to the registry directly" requires explaining and trusting a custom script. "I applied it via LGPO and `gpresult` shows it" is first-class
evidence.

For the foreseeable future, both mechanisms coexist:

- **LGPO-managed** — anything under `Software\Policies\...` or `Software\Microsoft\Windows\CurrentVersion\Policies\...`, or otherwise a
  documented GP policy. Telemetry, advertising, Defender, Copilot, Edge, Chrome, Office.
- **Direct registry (`Set-RegistryValue`)** — Explorer UI tweaks, taskbar alignment, Terminal delegation, GameDVR per-user toggles, anything
  that has no documented GP equivalent.

**Hard rule:** anything that has a documented policy equivalent goes via LGPO, even if direct registry would work. The audit story requires
consistency.

## Directory layout — source vs artifacts

The repository stores **policy sources** as plaintext `.txt` files under `resources/`. From these, the build pipeline produces **artifacts**
for different delivery mechanisms (local apply, domain GPO backup), written to the top-level `dist/` directory. The same source produces
both.

```text
resources/
  policies/                        # AUTHORITATIVE — hand-authored, committed
    00-example.txt                 # example policy source (never compiled)
    01-telemetry.txt               # (planned) telemetry restraint policies
    ...
    skeleton/                      # GPO backup templates with {{Placeholder}} fields
      Backup.xml
      bkupInfo.xml
  metadata/                        # ISO control mapping, justifications, owner
    00-example.psd1                # example metadata file
    01-telemetry.psd1              # (planned)
    ...
  README.md                        # this file — layout, workflow, audit

dist/                              # GENERATED — gitignored wholesale
  GP/
    local/                         # compiled Registry.pol for direct LGPO apply
    gpo-backups/                   # GPO backups from Build-GroupPolicyBackup, plus manifest.xml
    exports/                       # Export-LocalPolicy captures awaiting review
```

`resources/policies/` and `resources/metadata/` are committed to git, reviewed, and audited. Everything under `dist/` is build output —
regenerated by CI on every push, published to a releases archive on tag. Because `dist/` is a single top-level directory containing only
generated content, `.gitignore` is a single line (`/dist/`) with no risk of accidentally excluding source.

### Why `.txt` instead of `.lgpo`

Microsoft itself ships policy text sources as `.txt` files alongside the LGPO tool. The `.lgpo` extension has no formal definition and is
not required by LGPO.exe — it reads any text file via the `/t` flag. Using `.txt` keeps the format self-documenting, ensures broad editor
compatibility, and avoids confusion with a proprietary extension.

## Policy source file format (`.txt`)

The native LGPO input format. Plaintext, diff-friendly, supports comments via `;`. Each policy entry is exactly four lines:

```text
; Header — version and ISO control mapping
; Version: 2026-06-14-01
; Justification: Reduces telemetry attack surface; supports ISO A.8.16

; Disable Windows Diagnostic Data collection
Computer
Software\Policies\Microsoft\Windows\DataCollection
AllowTelemetry
DWORD:0

; Disable advertising ID (per-user preference)
User
Software\Microsoft\Windows\CurrentVersion\AdvertisingInfo
Enabled
DWORD:0

; Delete a value that may have been set previously
Computer
Software\Microsoft\Windows\CurrentVersion\Run
SomeUnwantedAutostart
DELETE
```

The four lines per entry are:

1. `Computer` or `User` — which hive scope the value lives in (case-insensitive).
2. Registry subkey path (no hive prefix — the scope above determines that).
3. Value name. Leave the line **empty** for a key's `(Default)` value; use `*` for `DELETEALLVALUES` and `CREATEKEY`.
4. The action, which is **case-sensitive**:

| Action                  | Result                                                                     |
| ----------------------- | -------------------------------------------------------------------------- |
| `DWORD:n` / `QWORD:n`   | Integer; decimal, `0x` hexadecimal, or negative (two's complement)         |
| `SZ:text` / `EXSZ:text` | String / expandable string, written **without quotes** — quotes are stored |
| `MULTISZ:one\0two`      | Multi-string; `\0` separates the strings                                   |
| `BINARY:de,ad,be,ef`    | Bytes as comma-separated hex                                               |
| `DELETE`                | Deletes the named value                                                    |
| `DELETEALLVALUES`       | Deletes every value in the key (value name `*`)                            |
| `CREATEKEY`             | Creates the key (value name `*`)                                           |
| `DELETEKEYS`            | Deletes the subkeys listed, `;`-separated, on the value-name line          |
| `CLEAR`                 | Marks the value not configured; a built `registry.pol` simply omits it     |

### Escaping, encoding, and whitespace

These rules were verified against LGPO 3.0 and are enforced by `Build-GroupPolicyBackup.ps1`. Where LGPO silently stores something other
than what was written, the build fails instead.

- **Backslashes:** in string data, `\\` is one backslash and `\0` is a NUL character. Any other backslash sequence is literal, so
  `SZ:C:\path` works — but `SZ:C:\0data` would store a NUL and is rejected; write `C:\\0data`.
- **Encoding:** LGPO reads a file **without a byte-order mark as ANSI**, corrupting non-ASCII values. Save sources as UTF-8 with BOM (the
  `.editorconfig` does this for `resources/policies/*.txt`). BOM-less files are accepted only when non-ASCII appears in comments alone.
- **Whitespace is data:** trailing spaces in a value line are stored. The pre-commit `trailing-whitespace` hook is disabled for policy
  sources for that reason. Whitespace-only lines and indented comments are LGPO format errors; comments start in column 0.
- **Integer range:** LGPO wraps out-of-range values (`DWORD:4294967296` becomes `0`); the build rejects them.
- **No text form:** the `**DeleteValues`, `**SecureKey` and `**soft.` directives, registry types other than those above, and strings with
  line breaks cannot be expressed. `Export-LocalPolicy.ps1` writes them as commented-out blocks and reports each one.

### Recommended header conventions

Every `.txt` policy source should include a comment header:

```text
; Version: YYYY-MM-DD-NN
; Title: Short human-readable title
; Owner: <role or name>
; Justification: Why these policies exist. Links to ISO controls.
; ADMX: <FileName>.admx, policy "<PolicyName>"
; Upstream: <URL to Microsoft documentation>
```

## Metadata file format (`.psd1`)

Sidecar metadata for each policy source. Auditor-facing documentation that doesn't fit cleanly in the `.txt` header. Example:

```powershell
@{
    SourceFile         = '00-example.txt'
    Title              = 'Telemetry and diagnostic data restraint'
    Owner              = '<your name or role>'
    IntroducedVersion  = '2026-06-14-01'
    LastReviewed       = '2026-06-14'
    IsoControls        = @(
        'A.5.34 — Privacy and protection of PII'
        'A.8.16 — Monitoring activities'
    )
    Justification      = @'
...multi-line justification text...
'@
    UpstreamReferences = @(
        'https://learn.microsoft.com/...'
        'ADMX: DataCollection.admx, policy "AllowTelemetry"'
    )
    AppliesTo          = @{
        WindowsEditions = @('Pro', 'Enterprise', 'Education')
        MinBuild        = 19041
    }
}
```

## Domain compatibility

The policy text files are **value-level** domain compatible — the registry paths (`Software\Policies\...`) are identical whether applied
locally or by a domain GPO. The _delivery_ differs:

- **Local apply:** `LGPO.exe /t source.txt` writes directly to local `Registry.pol`, or import a built backup with
  `Import-GroupPolicyBackup.ps1`.
- **Domain apply:** the same sources are compiled into a GPO backup (`Backup.xml`, `bkupInfo.xml`,
  `DomainSysvol/GPO/Machine|User/registry.pol`) and imported with `Import-GroupPolicyBackup.ps1 -Target Domain`.

### Lifecycle — `scripts/Policy/`

```text
golden image (gpedit)
      |  Export-LocalPolicy.ps1         local policy -> dist/GP/exports/*.txt   (review, prune, complete the header)
      v
resources/policies/*.txt
      |  Build-GroupPolicyBackup.ps1    sources -> dist/GP/gpo-backups/{BackupId}
      v
GPO backup
      |  Import-GroupPolicyBackup.ps1   -> local Group Policy (LGPO /g), or -> a domain GPO (Import-GPO)
      v
applied policy
```

**Export** reads `Machine\registry.pol` and `User\registry.pol` with PSFoundation's `ConvertFrom-RegistryPolicy`. It captures everything in
local policy — including settings that did not come from the golden-image configuration — groups entries under their top-most captured
registry key, and reports every group so nothing enters a baseline unnoticed. The metadata header is emitted as a TODO stub.

**Build** compiles the sources with `ConvertTo-RegistryPolicy` and needs no LGPO.exe. (It cannot delegate to `LGPO.exe /r`, which ignores
the `Computer`/`User` scope and writes both into one file.) The GPO backup is stamped from the templates in `resources/policies/skeleton/`:

- Every build gets a fresh GPO GUID and backup ID and is added to `manifest.xml`; existing backups are kept.
- The Registry client-side extension is registered for each side that carries settings. Without that registration, clients silently ignore a
  GPO's `registry.pol`.
- Domain provenance fields use synthetic values under the reserved `.invalid` TLD. `Import-GPO` imports into whichever domain it targets, so
  they are informational — the vendored templates carry no real domain data.
- `gpreport.xml` is not produced (LGPO's own `/b` backups omit it too); an empty report would misrepresent the backup when previewed in
  GPMC.
- `*-example.txt` sources are skipped. Sources are validated and the backup is assembled in a staging folder first — nothing is written if
  any source fails to compile.

**Import** validates the backup before applying it: readable `registry.pol` files, and the Registry extension registered for every side with
settings. With several backups present it requires `-BackupId` rather than guessing.

- `-Target Local` (default) runs `LGPO.exe /g` elevated. LGPO.exe must carry a valid Microsoft Authenticode signature.
- `-Target Domain` runs `Import-GPO`, which **replaces all settings** in the target GPO; `-DisplayName`, `-Domain`, `-Server`,
  `-CreateIfNeeded`, and `-LinkTarget` carry the per-domain values. Afterwards it warns when no principal holds the Apply Group Policy
  permission — such a GPO applies to no computer or user.

All three support `-DryRun` and `-PassThru`; `tests/Policy/PolicyPipeline.Tests.ps1` covers them without elevation, a domain, or LGPO.exe.

### Platform notes

- **Domain-only policies** (account lockout, Kerberos, password complexity): set as separate text files when authored, omitted from the
  local apply set, included only in the domain build.
- **GPO-level features** (security filtering, WMI filtering, loopback processing, link order): these are properties of the GPO object in AD,
  not of the registry values inside it. They're declared in the build step that wraps a source into a GPO backup, or applied at link time by
  the domain admin.

## Policy authoring workflow

1. Author or modify a `.txt` file in `resources/policies/` — by hand, or from a configured golden image via `Export-LocalPolicy.ps1`.
   Include the version comment in the header.
2. Author or update the matching `resources/metadata/*.psd1` with the ISO control mapping.
3. Validate with `Build-GroupPolicyBackup.ps1 -DryRun`, then test in a VM via `Invoke-LGPO -PolicyPath <file>` or
   `Import-GroupPolicyBackup.ps1`.
4. Verify the apply with `gpresult /h gpresult.html` and inspect the relevant section. The values from your policy source should appear in
   the report.
5. Commit both files in the same change. Reviewer checks both.

## LGPO behavior notes

### Additive application

`LGPO.exe /t <file.txt>` **adds or updates** the values in the file. It does **not** remove values that a previous apply set but that are
absent from the current file. So if you remove a policy entry from a source and re-apply, the old value stays in `Registry.pol` — the source
no longer reflects the actual applied state, which is an audit problem.

Two strategies for authoritative apply:

- **Wipe-then-apply:** before applying, delete the local policy store, then apply the full source set:

  ```powershell
  Remove-Item "$env:SystemRoot\System32\GroupPolicy\Machine\Registry.pol" -Force
  Remove-Item "$env:SystemRoot\System32\GroupPolicy\User\Registry.pol"    -Force
  Invoke-LGPO -PolicyPath <file.txt>
  gpupdate /force
  ```

  Clean and predictable. Suitable for image builds and maintenance windows.

- **Explicit DELETE entries:** when retiring a policy, change its block to a `DELETE` directive so the next apply actively removes the
  value. More surgical, preserves audit continuity (the history shows the value was explicitly retired), but requires discipline.

For the initial migration, **additive application is acceptable** because you're adding policies, not retiring them. Adopt the
wipe-then-apply pattern (or DELETE-directive discipline) once the policy set is mature.

### LGPO `/t` flag

The `/t` flag tells LGPO.exe to apply a text-format policy source (our `.txt` files). The `/g` flag applies a GPO backup directory.
`Invoke-LGPO` auto-detects which to use based on whether `PolicyPath` is a file or directory.

## Migration sequencing

Concrete order to move existing direct-registry policies into LGPO. This is months of work in total — but the function plumbing is done, and
each individual migration is a small, reviewable change.

1. Author the first policy baseline — pick something small like advertising-info disable. Run it through `Invoke-LGPO`. Verify via
   `gpresult /h`. This validates the end-to-end pattern.
2. Migrate one category at a time from direct-registry to LGPO. Suggested order:
   1. Telemetry (largest blast radius for the audit story)
   2. Defender
   3. Edge / Chrome / Firefox
   4. Copilot and Edge Copilot
   5. Office
   6. Advertising / suggestions / Cloud Content
3. Leave non-policy items on direct registry — Terminal delegation, Explorer UI tweaks, GameDVR per-user toggles. These have no GP
   equivalent.

## Audit concerns

### Versioning the LGPO binary

The weekly CI (via `Test-LGPOSourceAvailability`) catches URL availability. The content-drift hash check ensures the downloaded binary
matches the committed hash. A failed match means Microsoft updated the binary — pause, review, update `Resolve-LGPOSource`'s hash table,
commit.

### Versioning the policy baselines

Each `.txt` file carries a `; Version: YYYY-MM-DD-NN` comment. `Invoke-LGPO` logs which file (and therefore which version) was applied.
Combined with the structured return object's timestamp, you can answer "what policy was in effect on date X?" from logs alone.

### Intent vs observation

The `.txt` files in git are the _intent_. `gpresult` output post-apply is the _observation_. Proving they match is the _control_. The
planned (audit-report generator) compares parsed `.txt` against parsed `Get-LGPOAppliedState` output to produce a configured-vs-observed
diff.

### ADMX mapping

Auditors often want to see the link between your policy values and Microsoft's published ADMX templates. Include the ADMX file name and
policy name in the `.txt` comment header (and again in the metadata `psd1`):

```text
; ADMX: DataCollection.admx
; Policy: AllowTelemetry
; Microsoft documentation: https://learn.microsoft.com/...
```

### Don't auto-update LGPO in production

Pin the version. The CI tells you when an update is available; a human reviews, runs tests, and commits the version bump. "We track upstream
dependencies but apply updates only after review" is a stronger control claim than "we always use the latest".
